## 有程式碼依據的維護項目

### M01：API 身分與輸入驗證（會員端點已修補）

- 原因：收藏與回報原本相信客戶端 userId，且回報可夾帶未驗證欄位。
- 2026-10-30 修補：三個收藏／回報 handler 使用 getAuthUser，以 HS256 JWT 的 sub 決定會員；驗證 cafeId 格式；回報套用 schema 並移除額外欄位，不接受客戶端 relation 覆寫。
- 驗證：缺失、偽造、過期、空 sub token 回 401；傳入其他 userId 仍只操作登入者資料；非法回報回 400。
- 留待後續：公開 cafe/query 的逐筆 schema、批次／流量限制；本輪沒有修改搜尋端點，也未做正式環境利用或資料影響調查。

### M02：已回報狀態與 API 回應不一致（已修補）

- 原因：me 只選取 reports.id，既有 UI 卻以 report.cafeId 判斷已回報。
- 2026-10-30 修補：me 加入 cafeId；authContext 的型別縮限為實際回傳欄位；重複回報的 P2002 回傳 409，不調整 UI。
- 驗證：隔離與真實 DB 測試均通過；瀏覽器實際提交回報並重新整理，回報數與已回報狀態正確，重複 API 回報回 409。

### M03：密碼重設驗證與寄信結果（已修補）

- 2026-10-30 修補：reset API 使用 resetPasswordSchema.shape.password 驗證，保留現有前端只送 password 的格式；不改 UI 或密碼規則。
- 驗證：弱／空／錯誤型別密碼回 400，合法密碼進行 bcrypt hash 並清空 token／期限，失效 token 回 400。
- 本輪修補：`src/lib/mail.ts` 明確檢查 SDK 回傳 error 並拋錯，forgot-password API 回 500，移除寄送前的誤導 success 紀錄。隔離測試確認 provider 回傳錯誤不再顯示成功。
- Resend 連線已驗證：使用既有環境金鑰向官方 `delivered@resend.dev` 寄出一次測試請求，API 已接受；不等於真實收件或一般訪客可收信，完整紀錄見測試文件第三輪。
- 經明確授權寄 1 封普通測試信至 Resend 註冊信箱，信件 ID `01a18b52-aef2-788b-aed9-ab86b4ce691b`，後台狀態 Delivered。只確認收件伺服器接受，不代表收件匣位置或密碼重設信連結已完整驗證。
- 留待後續：帳號存在資訊揭露、請求頻率限制、驗證自訂網域以寄給一般訪客；寄送前儲存 token 的策略尚未變更。

### M04：收藏唯一性與同步（中）

- 已確認：`prisma/schema.prisma` 的 Favorite 沒有 userId/cafeId 複合唯一約束；API 使用 findFirst 後 create/delete。
- 已確認：`src/app/favorite/page.tsx` 刪除後重取清單，未呼叫 refreshUser；地圖及 ShopInfo 依會員 context 的收藏呈現。

- 建議：先確認與清理既有重複資料的需求，再設計唯一約束、操作語義與狀態同步。
- 驗證：快速連點、併發請求、跨頁導航及重新整理後狀態。

### M06：搜尋與詳情非同步狀態（待重現）

- 已確認：map hook 在 Google 搜尋完成後、DB 同步成功前就設定 lastFetchPos；失敗後同區域可能被距離條件略過。AbortController 用於本地 fetch，不涵蓋 Places 搜尋。
- 尚待處理：ShopInfo 切換 ID 時沒有清空舊資料或中止既有請求。
- 本輪已修補回報部分：檢查 response.ok，失敗保留表單與三語系通知；成功重取店家聚合、刷新會員狀態並關閉編輯，提交期間停用送出。隔離測試涵蓋失敗不刷新／關閉，成功才刷新詳情與會員。
- 待驗證：舊回應是否覆蓋新店家、載入中是否殘留舊資訊、錯誤／重試與聚合是否及時更新。
- 建議：先在慢網路與模擬失敗情境重現，再修正請求有效性與刷新策略。
